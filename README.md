You find something good at eleven in the morning and you are not going to read it at eleven in the morning. So you share it here — or tap the widget, which takes whatever is on the clipboard — and forget it. It goes in with the blogs you follow, and by the evening the pile has sorted itself out: titles filled in, new posts pulled down, most of them already on the phone whether or not there is any signal, the whole lot waiting on one screen. Some of it you read. Some of it you hand to [readback](https://github.com/MKS-01/readback) and listen to on the walk, thumb on a transport bar that keeps playing once the screen is off. The long ones you ask about first, and Gemini Nano tells you what's in them without the article ever leaving the phone. Then you set the timer, put the phone face-down, and actually read for twenty-five minutes — on **Paper Black**, a page rather than a screen, warm-white ink on matte near-black lit by one terracotta accent, or on **Ink**, the same page with the hue drained out entirely, which is where it starts.

There is no server, no account and no sign-up. What you subscribe to, you keep in your own Notion workspace — built and tended by Claude over Notion's MCP, read by the app over the plain API. Optional, and the app is complete without it.

| | |
|---|---|
| **Saved links** | Share sheet, paste field, or a home-screen widget that saves the clipboard in one tap |
| **Feeds** | RSS and Atom, synced on open, 15 posts deep per blog |

| **Readback** | Neural-TTS audio generated by [readback](https://github.com/MKS-01/readback), played through a foreground service |

| **NEXT UP** | An explainable ranking over links and posts together — every term visible in Settings |
| **Two themes** | Paper Black and Ink, swapped at runtime |

## Getting started

> **Android is the app; the other three are the workshop.** It's what this is built and tested against day to day. Desktop, web and iOS compile from the same source and are there to prove it travels — see [Platform support](#platform-support).

```bash
git clone https://github.com/MKS-01/duskread.git && cd duskread
./gradlew :androidApp:installDebug      # ~5 s once warm
```

That's the whole setup. Saved links, feeds, the widget, the timer and the themes all work the moment it opens. Notion and readback are both opt-in, and nothing nags you about either.

| | |
|---|---|
| **JDK** | 17 or newer — the toolchain targets JVM 17 |
| **Android** | 12 and up (`minSdk` 31, compile/target 36) |
| **Gradle** | 9.3.1, via the wrapper — don't install it yourself |
| **For summaries** | A phone with **AICore** — Pixel 9+, Galaxy S24+ and similar. No emulator has it |
| **For iOS** | Xcode, plus [XcodeGen](https://github.com/yonaskolb/XcodeGen) — the host project is generated, not committed |

<details>
<summary><strong>The other three targets</strong></summary>

```bash
./gradlew :composeApp:runDistributable              # desktop — see the note below
./gradlew :composeApp:wasmJsBrowserDevelopmentRun   # web, on :8080

cd iosApp && xcodegen generate && cd ..             # iOS needs an Xcode host
open iosApp/iosApp.xcodeproj
```

`runDistributable`, not `run`, for desktop: the embedded browser is Chromium
through JCEF, and its native side needs the packaged `.app` layout. Under a
plain `run` it segfaults during `CefApp.initialize`. Everything else in the
app works either way.

A first Kotlin/Native build for iOS is ten minutes or more; incremental after
that.

## What it does

### Saved links and feeds

**Save it however it reaches you.** Paste a URL into the field, or share one straight from Chrome — DuskRead is in the share sheet. Either way the row appears immediately with the host as its stand-in title, then a fetch fills in the real one behind it. A link that can't be fetched keeps a retry glyph rather than pretending it worked.

**Follow blogs by feed.** RSS and Atom, synced on open, cached so the list is instant. Posts land in Following on Home and read back exactly like a saved link does.

**Home suggests one.** `NEXT UP` ranks unread saved links and cached posts together — recency, the blogs and subjects you actually read, how long it is against the timer you have set, a nudge away from anything you just shuffled past. It is arithmetic, not a model, and **Settings ▸ Discovery** shows the top five with every contributing term broken out, so an odd pick is answerable rather than mysterious.

### The home-screen widget

Two things the app is for, one tap each, without opening it:

- **Save the clipboard.** An invisible activity reads it, files the URL, and the widget expands for a few seconds to confirm what it caught — the host, and whether it worked.
- **Start a focus session.** The countdown is a `Chronometer`, a real view in the launcher's process, so the launcher ticks it and this app is never woken to redraw.

Nothing polls. `updatePeriodMillis` is 0 and there is no periodic alarm, so an idle widget costs nothing at all.

### Offline

**Browsing never needs a network** — every screen renders from local storage. Reading usually doesn't either: when a feed carries the whole post, the body is cached at sync time and the reader opens it without a request. On one fourteen-feed catalogue that is **134 of 165 cached posts**, about 3 MB.

A post that will open offline says so on its meta line, and the badge is computed by the same code the reader itself calls — a badge that lies about this is worse than no badge. Feeds that publish summaries only can't be cached, and they're the ones that ask for a network.

### Notion sync (optional)

Follow the blogs listed in a Notion database, and keep saved links in step with it. Useful if you curate subscriptions somewhere other than the phone — or want newsletters that have no public feed to reach the reader anyway. **Skip this entirely and nothing is missing**: feeds can be followed by hand in the Following tab.

<details>
<summary><strong>Setting it up — about five minutes</strong></summary>

1. **Make a `Sources` database** with at least `Name` (title), `Feed URL` and `Active` (checkbox). Add a `Topic` select if you want the ranking to pool subjects across blogs. A site URL in `Feed URL` is fine — the app resolves it via `<link rel=alternate>`.
2. **Optionally make a `Reading List` database** for saved links. It needs `Title`, `URL`, `Duskread ID` (text), `Saved` (checkbox) and a `Status` — the full column list is in [docs/architecture.md](docs/architecture.md#notion-schema).
3. **Create a personal access token** in Notion's developer portal and copy it once.
4. **In the app:** Settings ▸ **NOTION** → paste the token → paste the **Sources database ID** (the 32-hex segment of the database's page URL) → optionally the **Reading List database ID** → **Test connection**, then **Sync now**.

**How it behaves after that:**

- **`Saved` is the gate.** Only ticked rows in `Reading List` come down to the phone; everything else stays in Notion as an archive.
- **It never deletes or archives a row.** Removing a link on the phone ticks `Dismissed` instead, so the refusal survives a reinstall.
- **A row removed from `Sources` does not unfollow the blog.** Unfollowing stays a deliberate act in the app.
- **The token is encrypted** — AES-GCM under a hardware-backed keystore key, in its own preferences file, never in the one the widget reads. **Disconnect** clears it and keeps your feeds.
- **Sync happens on open**, at most every four hours unless something local is waiting to go up, silently and in the background. There is no `WorkManager` job and nothing runs while the app is closed.

Why a pasted token rather than OAuth, and what would change that, is in [Authentication](docs/architecture.md#authentication).
</details>

### The database itself is built by an agent

There are two halves to the Notion side, and only one of them is in this repository.

**The app uses the [Notion API](https://developers.notion.com/reference/intro) directly** — REST, `Notion-Version: 2022-06-28`, a personal access token, no SDK and no JSON model. That half is `notion/` in `commonMain` and it does exactly two things: read `Sources`, reconcile `Reading List`.

**Everything upstream of that was done by Claude over Notion's MCP server**, part of the [Notion Developer Platform](https://www.notion.com/product/dev) — no glue code, no scripts in this repo, nothing scheduled:

- **Creating the two databases** to the schema in [docs/architecture.md](docs/architecture.md#notion-schema) — columns, types, select options, and the views that make the table usable by a human afterwards.
- **Filling `Sources`, and checking its work.** Every candidate feed address was actually fetched and tested for an RSS or Atom root element before the row was ticked `Active`. That pass is what caught the usual failures: a blog registered by its site URL rather than its feed, a publication whose feed lives on a different subdomain, a "no feed available" that turned out to serve 76 entries. Four rows ended up `Active = false` with a `Feed status` saying why — which is a better outcome than the app silently fetching HTML and finding no entries.
- **Backfilling the archive** — a run of recent posts filed as `Reading List` rows with dates, excerpts and topics, so the ranking had something to work with on day one.
- **Filing newsletters that have no public feed.** Mail connected on the same side, read, and filed as a row. Tick `Saved` and it's on the phone at the next sync — see [Flow 3](docs/architecture.md#flow-3--newsletters-from-inbox-to-phone).

**Why the split is worth having.** Schema changes, bulk verification and one-off backfills are exactly the work that would otherwise become a settings screen nobody wants to use — or a maintenance script nobody wants to own. Leaving them to an agent against a real API kept the app to the part that has to be fast and offline, and kept this repository free of a second integration.

**And it is where the personalisation lives.** `Topic` on a source is a Notion select, and the ranking reads it — so tuning what Home puts in front of you is editing a row, not shipping a build. Same for what you follow, what's archived, and what comes down to the phone at all. Ask for it in a sentence:

> *"Add Julia Evans' blog to Sources under Topic = Engineering, check the feed URL resolves, and untick anything in there that hasn't published in a year."*

The app is the reader. The agent is the librarian. Neither needs to know much about the other, because the schema is the whole contract between them.

### Readback

**Generation happens elsewhere; this app just listens.** [readback](https://github.com/MKS-01/readback) runs on a Mac and turns articles into neural-TTS audio, writing a `library.db` and an `audio/` folder. You sync that folder to the phone yourself — its own script, run whenever you like.

Point DuskRead at it once, through the system folder picker in the Readback tab:

- **Pick the `readback-audio-db` root**, not `audio/` inside it. Choose wrong and you get a message saying so, rather than a permanently-empty list.
- **The grant persists.** Android's scoped storage means a folder is opened once and remembered; there's nothing to re-do after a reboot.
- **Strictly read-only.** DuskRead copies `library.db` into its cache to query it and never writes back — the sync direction is one-way by design.

Playback runs in a foreground service with a media notification, so it survives leaving the app, and the floating bar at the foot of Home turns into the transport when something's playing.

### On-device summaries

Summaries go through [ML Kit GenAI](https://developer.android.com/ai), which routes to **Gemini Nano** via AICore on supported hardware. The app asks for article summarisation only — one bullet or three, folded into a paragraph — and lets the system pick the register. There's no prompt to write and nothing to configure beyond how long a summary you want.

- **First run downloads the model.** AICore handles it; it takes a moment once and never again.
- **Two ways in** — swipe a row in Saved, or the toolbar control inside the reader.
- **Nothing leaves the phone.** No API key, no request, no article text on a wire.
- **Off Android it's simply absent.** The same UI compiles against a stub that reports itself unavailable, so the control just isn't drawn and nothing upstream has to care.

### Focus timer

A pomodoro that behaves like an alarm and not a widget: a real system notification and a vibration when the interval ends, so it works with the phone face-down and the app closed. It lives on Home beside the reading, because the point is to read for twenty-five minutes rather than to admire a timer — and it's the second half of the home-screen widget, so a session can start without opening anything.

## How it's built

### Platform support

**Android is the app; desktop, web and iOS are how the shared code and the
design system get exercised off a phone.** Everything runs everywhere, but
readback needs a filesystem and summaries need AICore, so both are Android
first and desktop second — `summariesSupported()` and `readbackSupported()`
are `expect`/`actual` constants, and a screen asks before it offers, so a
control that could only disappoint is never drawn.

### Tech stack

[Compose Multiplatform](https://www.jetbrains.com/compose-multiplatform/) 1.11
and Material 3 on Kotlin 2.3, one source set for all four targets — everything
but the leaf nodes is shared, and the platform seams are `expect`/`actual`
pairs: storage, secrets, audio, the summariser, the timer, the HTTP client.
State is a `HomeTab` enum and overlays in one `Box`, hoisted into `App.kt` over
a flat key/value store; no nav library, no ViewModel, no DI, no database.
[Ktor](https://ktor.io/) 3.1 does the network with a different engine per
target, [ML Kit GenAI](https://developer.android.com/ai) routes summaries to
Gemini Nano, [sqlite-jdbc](https://github.com/xerial/sqlite-jdbc) and SAF read
the readback library, [KCEF](https://github.com/DatL4g/KCEF) is the desktop
browser, and [Haze](https://github.com/chrisbanes/haze) is the blur behind the
floating bar. Built with AGP 9's `androidLibrary` KMP DSL on Gradle 9.3.1.

```bash
./gradlew ktlintCheck    # lint; several rules deliberately off, see .editorconfig
./gradlew ktlintFormat   # auto-fix
```

No tests yet — verification is a build, a lint pass and the app on a device.

## Design system

Two schemes, one layout, both dark: **Paper Black**, warm-white ink on matte near-black lit by one terracotta accent that means only *there is sound here*, and **Ink**, the same page with the hue drained to luminance alone — the default, and what it persists to. The app swaps between them at runtime, so no screen hard-codes a colour: it comes from `MaterialTheme.colorScheme` (`ui/theme/Theme.kt`), sizes that carry a decision from `ui/theme/Tokens.kt`, icons from `ui/theme/DuskReadIcons.kt`.

Everything else visual is specified on the page — **[mks-01.github.io/duskread](https://mks-01.github.io/duskread/)**, or `docs/design-system/design-system.html` in a checkout.
