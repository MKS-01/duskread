Screen — Article summary

On-device, from the reader and from a swiped row

A local-model summary (ML Kit GenAI → AICore), generated from the text InAppBrowserScreen extracts into Article.text when a reader view opens, or from a fetch when a list row asks. Lives in summary/ and ui/summary/. A few decisions behind the built version are worth calling out:

  • Prose, not bullets. The concept drew a gist line and three bullets. What shipped is a single paragraph in a single tone — a summary of an argument asks the reader to reassemble it from fragments otherwise, which is most of the work they opened the panel to avoid. The engine returns bullets always, so parseSummary flattens them into prose rather than the panel growing a layout per engine mood.
  • Two lengths, on the engine's own dial. Settings offers Short and Full, mapped to AICore's ONE_BULLET and THREE_BULLETS — genuinely different answers, not one trimmed from the other. A word limit was tried first and dropped: a limit can only cut, never lengthen, and three points from this model often run under any ceiling worth naming, so every setting produced the same text. Two settings that always differ beat three that usually don't. The chips are described by what you get to read, never by the number of points — that number is an AICore implementation detail and means nothing to someone deciding whether to open an article.
  • One engine, no model picker. There were two paths — AICore's free-form Prompt API first, the purpose-built summarisation feature as fallback — because only the former could be pointed at the Gemma 4 preview. On real hardware the Prompt API answers FEATURE_NOT_FOUND, so it and the three-model Settings picker that depended on it are both gone. The remaining feature takes no model preference, and a control that selects between identical outcomes is worse than no control.
  • A list row can ask too. The concept ruled the list out. Saved already teaches swipe-left-to-remove, so swipe-right-to-summarise is the mirror of a gesture that exists, and triaging a list is exactly when a summary is worth most. SummariseBackground draws it in surfaceContainerHigh, not Remove's accent container — one is destructive and should look like it.
  • One shared pill. ui/summary/SummaryChip.kt is the download button, in the panel and in Settings alike — bordered, mono-uppercase, Radius.Chip, accent and border, never a fill.

Reader toolbar, not the list. A summary needs Article.text, which only exists after extraction — running that (and a local-model pass) for every row in Saved or Readback would mean summarising links nobody opens. The button lives beside the existing Reader-view toggle, hidden (not disabled) until extraction has produced text, matching that toggle's own rule.

Inline spinner, not a blocking screen. The article is already readable while the model runs — the icon swaps for a small spinner in the same 34px slot, nothing else on screen changes.

Floating, not full-screen. Same instinct as the toast and the nav bar: a panel that sits over the reader rather than replacing it, dismissible with the corner close glyph or a tap outside, so checking the summary never costs your scroll position in the actual article.

The model (as built): ML Kit's on-device GenAI Summarization API, Android-only, behind an expect/actual the way ReadRepository and AudioPlayer already are — other platforms would hide the button the same way Readback's folder picker differs per platform today. The prerequisite, Article.text, already exists; nothing about extraction is new work.

Wide — desktop and web

One breakpoint, and the bar stops floating

Planned, not built. Desktop opens at 1180×820 (Main.kt) and web at whatever the tab is, and both currently render the phone layout stretched to fill it — a saved-link title runs past 100 characters on one line, and the floating bar sits at the bottom of a window nobody is holding. Nothing in commonMain reads the window size today. This section is the plan for when it does.

BreakpointLayout.TwoPaneBreakpoint = 720.dp — one threshold, not a five-class ladder. Below it the phone layout is used unchanged, including in a narrow desktop window; above it, two panes.
Rail44dp, left, hairline on its right edge. The three tabs go vertical; the selected one keeps the surface lift it has today and gains a 2dp accent tick on the outer edge.
List paneFixed 380–420dp. Fixed, not proportional — a list of two-line titles has a correct width and a 2560px monitor does not change it.
Detail paneFills the rest; its content is capped at 68ch and left-aligned against the pane's own gutter, not centred in the window.
GuttersReadingGutter 18 → 28dp, ListGutter 14 → 20dp. Type sizes do not change at all.
TransportFull-bleed along the bottom, above nothing. The only element that keeps its phone position, because it outlives whichever pane is open.

The bar stops floating. On a phone it sits at the bottom because that is where the thumb is. On a desktop there is no thumb, the pointer is already wherever the eye is, and the bottom edge of an 820dp window is simply the longest journey from the list — so navigation goes to a left rail and only the transport stays bottom, full-bleed, because it is the one thing that outlives the pane above it.

The list pane is a fixed width, not a fraction. Two-line titles have a correct measure and a wider monitor does not change it; a percentage would just make the same four rows emptier.

Nothing gets bigger. Titles stay at their phone size, the waveform keeps its 2dp bars, rows keep their hairline. Only the gutters open up. Scaling type with the window is the fastest way to turn a considered phone screen into a generic desktop one.

Three states a phone never needed

Touch has one state worth drawing: pressed, and it is gone before you look at it. A pointer hovers, a keyboard focuses, and a two-pane layout has to say which row the right-hand side belongs to. None of these exist in the app today and none of them may use colour — the accent still means there is sound here.

Hover is 3.5% white, not a border. A border on hover shifts every row by a pixel as the pointer travels the list; a ground wash does not move anything. Selected is the same surface lift a card already uses — no new value, and it survives Ink intact. Focus is the one place a hairline accent ring is allowed, because a keyboard user with no visible caret has nothing else to go on; it is an outline drawn inside the row's own bounds, so it too moves nothing. In Ink all three collapse to luminance, exactly as everything else does.

Keys

Deliberately few, and deliberately the same ones readback's own terminal player uses — the two projects are read by the same person on the same evening and should not disagree about what space does.

Playspace play / pause the transport, from any pane
Seek← → ±5 s
Move↑ ↓ through the list pane, enter to open in the detail pane
Paste⌘V anywhere on Saved fills the paste field, no click first
Dismissesc closes the topmost overlay — the same single PlatformBackHandler Android's gesture already goes through

No shortcut opens a pane that a tab does not. Every key here either drives the transport or moves a selection; none of them are a hidden route to a screen, which keeps the rail the only answer to "where am I?" and means the phone build loses nothing by having no keyboard.

Overlays, at width

Focus, the summary panel and the reader are overlays in one Box rather than destinations, and that stays true when the window is wide — but a bottom-anchored sheet spanning 1180dp is a banner, not a panel.

  • The summary panel anchors to the detail pane, not the window: same Radius.Card, same hairline, bottom-right of the pane that asked for it, capped at 420dp wide. Its job is to sit beside the article you are deciding about, and at this width it can do that without covering it at all.
  • Focus becomes a centred panel, ~440dp, on a dimmed ground — not a full-screen takeover. The phone version goes full-screen because a phone has no room to be beside anything; a desktop window does, and blanking 1180×820 to show a clock is theatre. The bottom-anchored, thumb-zone rule that put the meter low on the phone has no counterpart here: centred is correct once nothing has to be reachable.
  • The reader stops being an overlay at all. It is the detail pane. Android's in-app browser is a platform overlay because the phone has one column; with two, opening a link fills the right-hand side and the list stays visible beside it — which is the entire argument for two panes.
  • Nothing gains a modal. No dialog, no confirm step. Removing a saved link is still a swipe on touch and a row action on pointer, undone from a toast either way.

What web has to answer that desktop does not

  • No readback library. The folder picker is Android SAF and desktop file-path; a browser tab has neither, so Readback in Wasm shows the same "not configured" state it does now and the rail's Readback tab stays visible but empty. Not hidden — a missing tab is a worse answer than an empty one.
  • No summaries. Same as iOS: summariesSupported() is false, the control is not drawn, and nothing upstream knows.
  • The window is not yours. A tab can be 320dp or 3000dp and can change mid-session; the breakpoint has to be read continuously rather than at start-up, which is the one place BoxWithConstraints earns its keep over a platform window-size class.
  • Fonts arrive late. Jost and Inconsolata are bundled resources on the other three targets and a network fetch on web. The first paint has to be legible in the fallback stack rather than invisible, so no font-display: block equivalent — accept the swap.

Monochrome

Ink — a second design, not the first one with the colour deleted

The hue drops to nothing and level is carried by luminance alone — the interface was already greyscale, so the idea survives intact. Reachable from the tab bar's contrast toggle or Settings; the choice persists across restarts and flips the Android launcher icon and splash to match.

Brand

Dusk bar — one shape, a crescent bitten out

The house language ("the waveform is the alphabet") carries into the mark itself: one wide bar — read, listen — with a crescent bitten from its top, for dusk.

The bite is painted as an opaque circle in the exact ground colour, drawn after the bar — not a fillType="evenOdd" subtraction, which was tried first and is wrong for a cut shape that extends outside the base shape: evenOdd fills that outside part back in as a second, disconnected blob instead of letting it vanish. The one place the ground-colour trick can't apply — the Android 13+ themed-icon layer, which reads only alpha, no colour — keeps a true evenOdd hole instead, sized down to sit fully inside the bar so the same bug can't recur there. The mark still settles into place on boot the same way the one before it did. The launcher icon and splash are this Ink mark permanently now, not one half of a pair that swapped with the in-app theme — see "In use today" below.

Icon set

Bar — the waveform is the alphabet

One stroke spec throughout: 2.4 weight, round cap and join. Every glyph that can be built from evenly spaced vertical bars is — readback, feed, offline, settings (the sliders are bars) — and the rest borrows the same weight and terminal so the set still looks cut from one clip. This is the mockup's original demo wall, kept as the stroke reference — it is not a mirror of ui/theme/DuskReadIcons.kt. The shipped set is 22 icons and diverges both ways: search, share, sleep, speed, skip, queue, add and delete below were never built (no playback-speed, sleep-timer, search or share feature exists), while the code has several this wall doesn't show — Target, Clock, Shuffle, FolderConnect, BookmarkFilled, Reader, Check. offline below is shipped as DuskReadIcons.Offline — the wall's own bars, exact same path, reused rather than redrawn.

In use today

What's actually shipped

Cross-checked against the current codebase, not carried forward from the old migration notes unverified.

  • No card boxes anywhere. Home, Readback, Saved, Following and Settings all sit flush on the background, separated by a bottom hairline (ui/common/ListRow.kt). The Following post carousel and feed-management list, once boxed, are flat now too.
  • One shared row skeleton. ListRow/ListRowBody/ListRowDivider hold the sourcechip-title-meta shape everywhere it appears, instead of three hand-rolled copies. RowTone (Normal/Accent/Faded) names the states a row can be in.
  • Two colour schemes, real tokens, one is now pickable. ui/theme/Theme.kt's DarkScheme (Paper Black) and MonoScheme (Ink) — both dark, mono is the same layout with hue drained to luminance alone. Paper Black's accent is an AccentColor — terracotta #C6684A or a dusty green #4FA870, built at the terracotta's own saturation and lightness so neither reads louder than the scheme was designed to carry — chosen in Settings and defaulting to terracotta. Ink ignores it; the Settings swatches themselves grey out while Ink is active, the same "nothing but lightness left" rule as everywhere else.
  • Ink is the default, and persists — but the launcher no longer follows it. UserPrefs.mono defaults to true and survives restarts. The home-screen icon and splash used to swap between a Paper Black and an Ink pair via a pair of Android activity-aliases (LauncherPaper/LauncherInk); that mechanism — and the orange launcher assets it switched to — is gone. The app icon is Ink's white mark on its dark tile, always, regardless of which scheme is active in-app.
  • Radius.Chip (3dp) is the shared corner for anything hairline-bordered and squared-off: sort chips, the sourcechip, and — as of this pass — the Settings and folder icon buttons, both now bordered squares rather than bare glyphs.
  • Jost + Inconsolata throughout, replacing Space Grotesk and each platform's default mono.
  • DuskReadIcons.kt holds 22 stroked vector icons in the Bar hand (2.4 weight, round cap/join) — see the Icon set section above.
  • The floating nav bar carries three tabs, the transport when something's playing, and the Ink toggle behind a divider.
  • AppTextField is the one text-field shape in the app — hairline border, Radius.Inline (10dp), never a pill — used by every field: Saved's paste field, the feed-follow field, Settings, the desktop folder path, onboarding, and Focus's new custom-length entry.
  • Launcher icon and splash fill ~70% of their canvas, solid rather than alpha-stepped, animating the outer bars to rest on boot.
  • On-device summaries, running on real hardware. ML Kit GenAI's summarisation feature against AICore, confirmed end to end on a Galaxy S25 (SM_S931B) — download, generation and the panel. Note that an emulator cannot stand in for this: those system images carry no com.google.android.aicore, so the engine can only ever answer "unavailable" there.
  • The summary panel (ui/summary/SummaryPanel.kt) is bottom-anchored and floats over whatever asked for it — the article in the reader, the list under the overlay — on surfaceContainerHigh with a hairline border and Radius.Card. It is never a destination: the point of summarising is deciding whether to open the thing, and a full-screen answer has already taken you away from the list you were triaging.

Next

Genuinely still open

Re-verified against the current code — some items the old migration notes flagged (Readback's sort pills being filled surfaces, Following still boxed) are already fixed and dropped from this list.

  • Saved's "From clipboard" suggestion and one paste-row fill are still filled surfaceContainer/primaryContainer boxes (LinksTab.kt) rather than a bordered pill.
  • Nothing reads the window size. Desktop opens at 1180×820 and web at whatever the tab is; both get the phone layout stretched, with titles running past 100 characters and a floating bar at the foot of a window nobody is holding. The plan is in Wide — desktop and web above: one TwoPaneBreakpoint, a left rail, a fixed list pane and a capped measure. None of it is built.
  • There are no hover or focus states anywhere in the app, because touch never needed them. A pointer and a keyboard both do — see the three states in the Wide section.
  • Desktop has no app icon — compose.desktop.application.nativeDistributions sets no iconFile.
  • iOS and Wasm haven't been compiled across this whole design pass — a cold Kotlin/Native build is ten-plus minutes, so it's deliberately been skipped; one run should happen before calling any of this settled on those platforms.
  • Cut features awaiting a call, not a bug: the read-along highlighted-excerpt view and the "Read original" external-link row (both real, both cut when Readback went to two-facts-and-a-waveform), and the floating bar's ambient background waveform (moirés into a hatch at the row pitch).
